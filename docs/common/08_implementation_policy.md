# 08 Implementation Policy

## 目的

このドキュメントは、どのプロジェクトでも共通に使う実装・設計の判断基準を定義する。
`Requirements.md` から `03_detailed_design.md` へ落とす時に、動作の一貫性を保つための共通ルールとする。

## 共通原則

- 業務ルールは Controller ではなく Service に置く。
- View は表示に専念し、業務判定を持たない。
- Model はテーブルと関連を表す。
- 副作用のある処理は、必ずトランザクション境界を明示する。
- 状態変更は、状態遷移の条件を明文化する。
- 重複や二重実行があり得る処理は、冪等性または競合制御を設計する。

## トランザクションとロック

- 複数テーブルを更新する処理は transaction を基本とする。
- 同時更新の可能性がある箇所は lock を検討する。
- 定員、未処理件数、同日一回などの競合は、DB 制約とアプリケーション判定を併用する。
- 一度の操作で複数状態を更新する場合は、更新順序を固定する。

## 冪等性

- 重複送信されても同じ結果に収束する処理は冪等として扱う。
- 同一ユーザー・同一対象の二重作成は、原則として既存データを返すか、明示的に拒否する。
- 冪等性の扱いは、仕様と詳細設計の両方に記載する。

## 状態遷移

- 状態を持つデータは、許可する遷移を明示する。
- 状態値は文字列か数値かを統一して定義する。
- `pending / approved / rejected` のような審査系状態は、未処理からの遷移のみ許可する。
- `entry / cancelled` のような利用系状態は、キャンセル条件を明示する。

## 例外とHTTP status

- 想定内の業務エラーは明示的に投げる。
- Web は画面に戻す。
- API は JSON で返す。
- 認可不足は 403 を基本とする。
- 競合は 409 を基本とする。
- 入力不備は 422 を基本とする。
- 想定外は 500 とする。

## 設計書への書き方

- `01_specification.md` では、業務ルールと状態を明記する。
- `02_basic_design.md` では、画面・API・DB・処理の対応を明記する。
- `03_detailed_design.md` では、トランザクション、ロック、冪等性、例外処理を明記する。
- 実装に影響する内部ルールは、コードだけでなく設計書にも残す。

## 具体的に共通化すべきもの

- 競合制御の方針
- 冪等性の扱い
- 状態遷移ルール
- 例外の返し方
- 更新順序
- DB 制約を使う箇所
- Service が真実になる箇所
