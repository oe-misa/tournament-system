# 09 Spec Document Standards

## 目的

このドキュメントは、`01_specification.md` / `02_basic_design.md` / `03_detailed_design.md` をどのプロジェクトでも同じ書き方で作るための標準を定義する。

## 共通ルール

- 事実、制約、判断基準、未確定事項を分けて書く。
- 仕様は曖昧な表現ではなく、テスト可能な粒度で書く。
- 画面名、API 名、データ名、状態名、条件は具体名で書く。
- 1 文で複数の判断を混ぜない。
- 実装に影響する内部前提は省略しない。
- ただしコードの変数名や private helper の分割理由までは書かない。

## 01_specification.md の標準

### 役割

- 何を作るかを定義する。
- 業務ルール、対象ユーザー、画面、データ、権限を明確にする。
- 後続の設計ができるだけの材料を揃える。

### 書く粒度

- 機能単位で記述する。
- 画面から見える振る舞いと、業務上の制約を明記する。
- 状態遷移、入力条件、出力条件、保存先は明記する。
- 内部実装のうち、挙動に影響するものは書く。

### 含めるべき項目

- 目的
- ユーザー種別
- 機能仕様
- 画面や操作の振る舞い
- 業務制約
- 状態
- 保存先
- 主要データ
- 未定義・今後検討

### 書き方の基準

- `できる/できない` を明確にする。
- `いつ/誰が/何を/どこに` を書く。
- 1 機能ごとに、少なくとも利用者・入力・出力・保存先・制約を持たせる。
- 仮説と確定を混ぜない。

## 02_basic_design.md の標準

### 役割

- 画面、API、DB、処理の全体像を整理する。
- どの画面がどの API / Service / DB に繋がるかを定義する。
- 主要な処理フローを把握できる状態にする。

### 書く粒度

- 画面一覧、ルート一覧、API 一覧、DB 概要を必ず持つ。
- 主要処理はフロー図相当の番号付きステップで書く。
- Controller や Service のクラス名は必要なら書くが、詳細なメソッド単位には落としすぎない。
- 画面とデータの対応、処理の流れ、権限の対応を明確にする。

### 含めるべき項目

- システム構成
- 画面一覧
- Web ルート
- API
- DB 概要
- 主要処理の全体像

### 書き方の基準

- 画面と処理の対応関係が追えること。
- 01 の要件がどの画面・API に落ちるかが分かること。
- 03 に渡すために、処理の大枠と責務分担を固定すること。

## 03_detailed_design.md の標準

### 役割

- Controller / Service / Model レベルの実装方針を定義する。
- 入出力、分岐、例外、保存単位、更新順序を具体化する。
- コードを書く前に迷わない状態にする。

### 書く粒度

- クラス単位、メソッド単位で書く。
- どのメソッドが何を受け取り、何を返すかを書く。
- どの Service が真実を持つかを書く。
- transaction / lock / 冪等性 / 状態遷移 / HTTP status を明記する。
- 画面や API の成功・失敗時の返し方を書く。

### 含めるべき項目

- Controller
- Service
- Model
- Support
- 返却値
- 例外処理
- 更新順序
- 保存先
- 競合制御

### 書き方の基準

- 実装者がコードを書けるだけの具体性を持たせる。
- 仕様を満たすための内部前提を明記する。
- private helper の分割理由や変数名の詳細は省略してよい。
- 画面文言の最終表現は省略してよい。

## 3 層の関係

- `01` は「何を作るか」を定義する。
- `02` は「画面・API・DB の全体像」を定義する。
- `03` は「どう実装するか」を定義する。
- `03` は `02` に書かれた処理を、コードに落とせる粒度まで細かくする。

## 禁止事項

- `01` に実装手順を書きすぎない。
- `02` にメソッド詳細を書きすぎない。
- `03` にコードの逐語的な書き方を書きすぎない。
- いずれの設計書でも、未確定事項を暗黙に確定させない。
