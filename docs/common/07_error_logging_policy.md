# 07 Error Logging Policy

## 目的

このドキュメントは、プロジェクト横断で共通に使うエラー処理とログ出力の標準を定義する。

## 基本方針

- 想定内の業務エラーは、ユーザーに意味のあるメッセージで返す。
- 想定外のシステムエラーは、内部ログに残しつつ汎用エラーで返す。
- 業務エラーとシステムエラーを分離する。
- 秘密情報や個人情報をログに出しすぎない。

## エラー分類

### 業務エラー

ユーザーの状態、権限、操作順序で正常に拒否するもの。

扱い:

- Web はメッセージ付きで元画面へ戻す。
- API は適切な HTTP status と JSON を返す。
- 原則として error log には出さない。

### 認可エラー

権限不足による拒否。

扱い:

- 403 を返す。
- 必要に応じて監査ログ対象にする。

### バリデーションエラー

入力値不正。

扱い:

- Laravel の validation で処理する。
- Web はフォームへ戻す。
- API は 422 を返す。

### 競合エラー

同時更新、状態変化、二重送信によるもの。

扱い:

- 409 を基本とする。
- 必要に応じて transaction や lock を使う。
- 想定内なら error log に出さない。

### システムエラー

DB 障害、未定義例外、実装不備など。

扱い:

- Laravel 標準ログへ記録する。
- ユーザーには汎用エラーを返す。
- 再現に必要な request 情報を残す。

## HTTP status 基準

| Status | 用途 |
| --- | --- |
| 200 | 成功 |
| 201 | 作成成功 |
| 302 | Web の遷移 |
| 403 | 権限不足、業務上の実行不可 |
| 404 | 対象なし |
| 409 | 状態競合、重複、処理済み |
| 422 | 入力不備 |
| 500 | 想定外の障害 |

## ログ基準

- パスワード、トークン、セッション ID は出さない。
- 個人情報は必要最小限にする。
- 監査が必要な操作は別途監査ログとして設計する。
- request_id、user_id、route、method は障害調査に有用なら残す。

## 共通実装方針

- Service では業務エラーを明示的に投げる。
- Controller は Web と API で返し方を分ける。
- 例外の握りつぶしはしない。
- 同じ種類の障害は同じ扱いに統一する。
